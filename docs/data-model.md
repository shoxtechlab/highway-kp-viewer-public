# データモデルと公開範囲

更新日：2026年11月6日。[資料一覧](README.md)

Highway KP Viewerは、路線・区間・KP体系を区別してデータを管理します。この文書では、画面とAPIの位置表現、管理範囲の参照、開発元の分割形式を説明します。具体的な路線ファイルや補正点を公開する資料ではありません。

## 1. 現在のデータ構成

APIとデータ作成側が扱う主な生成物は次のとおりです。

- `road.json` — 路線情報、施設、橋梁、トンネル
- `route.geojson` — 上下線の線形と補正済みKP
- `route-scopes.json` — 管理事務所などの表示範囲

`road.json`というファイルを静的配布しなくても、施設・構造物等の表示内容は路線APIから返します。高精度な`route.geojson`全体はブラウザへ返しません。これらを一括して「すべて非公開のデータ」と扱わないことが重要です。

路線ごとにKP体系や位置の持ち方が異なるため、ビルド時に`lib/dataCompiler.mjs`が表現を正規化し、ファイル間の参照関係を検証します。既存Viewerは、この処理で生成された従来互換形式を引き続き読み込みます。

## 2. 位置の内部表現

KP位置は内部で「区間」と「その区間のKP」の組として扱います。

```json
{
  "section": "joban",
  "kp": 69.1
}
```

単一路線ではAPIの`section`は通常`null`です。複数のKP体系を持つ路線では、`section`によって同じ数値のKPを区別します。APIは現地の路線KPである`localKp`と、内部の表示軸である`routeKp`も区別します。特殊KP体系のすべてを既に実装しているという意味ではありません。

| 値 | 用途 |
| --- | --- |
| `route` / 路線ID | APIや保存データで対象路線を識別 |
| `section` | 同じ路線内の構成区間を識別 |
| `localKp` | 現地表示に合わせた路線KP |
| `routeKp` | 連結・不連続・表示位置計算の内部軸 |
| 追加データの`kpSystemId` | 入力したKPがどの体系に属するかを識別 |

KPの表示桁数を変更しても、保存値を一律に丸める必要はありません。橋梁・トンネルのポップアウト表示はKPを小数第3位・延長を1m単位に丸めますが、追加データのファイル書出は保存値を保持します。OSM由来の延長は諸元表示から除外します。

KPと座標を相互変換する処理は、[KP・座標変換アルゴリズム](kp-coordinate-algorithms.md)を参照してください。

## 3. 管理範囲の参照

管理事務所などの表示範囲は、施設名やKPを直接複製せず、安定した施設IDで参照します。

- `data/facility-registry.json` — 境界に使う施設のID、名称、区間、KP
- `data/scope-definitions.json` — 始点・終点となる施設ID

ビルド時に両者を解決して、従来互換の`route-scopes.json`を生成します。施設名やKPを変更するときは登録元を1か所直せばよく、表示範囲との不整合を防げます。

## 4. 路線データの分割

以下は非公開の開発元における構成説明です。公開スナップショットには路線別ファイルを含めません。移行済み路線では、編集元を`data-source/<route>/`へ分割します。

```text
data-source/e4/
├─ metadata.json    路線ID、名称、データ状態
├─ network.json     路線長、区間、端点
├─ facilities.json  IC、JCT、SA・PA
└─ structures.json 橋梁、トンネル
```

ビルド、ローカルAPI、R2同期では、これらを既存の`road.json`形式へコンパイルします。未移行路線は従来の`data/<route>/road.json`を正として扱うため、一斉移行を必要としません。

## 5. 移行時のルール

この節のコマンドは、必要な元データを持つ非公開の開発元向けです。

新しい分割元が一部だけ存在する状態は許可しません。`data-source/<route>/`を作成した路線では4ファイルをすべて必須とし、不足があればビルドを停止します。

```powershell
npm run migrate:road-source -- e17
npm run validate:data
npm run build
```

`npm run build`は公開用ビルドであり、`road.json`と`route.geojson`を含めません。
非公開データを含むローカル確認用の生成物が必要な場合だけ、明示的に
`npm run build:private`を使用します。公開用ビルドは生成後にも禁止ファイルを
検査し、混入があれば失敗します。

移行コマンドは、既存の分割元を上書きしません。移行直後には分割データを再コンパイルし、従来の`road.json`と意味的に一致することを確認します。移行期間中の旧ファイルは互換性確認用として残しますが、生成物は分割元から作成します。

## 6. 公開範囲

公開リポジトリには、このデータモデルとAPIインターフェースを理解するための資料を収録します。高精度な路線線形、KP補正点、OSMの中間生成物、路線別の加工設定は公開しません。

OSM由来データの扱いは、[OpenStreetMap由来の路線データについて](osm-derived-route-data.md)を参照してください。

## 7. 基礎データと追加データ

IC・橋梁・トンネル等の基礎データと、編集モードの追加データは別管理です。端末保存はIndexedDB、共有保存はD1です。追加レコードは`routeId`と`kpSystemId`、`startKp`、必要なら`endKp`を持ちます。全国版・管理事務所版等の入口によってレコード自体を複製しません。

追加データのJSON・CSV形式、IDによる更新、公開範囲、競合検出は[編集モード仕様](user-annotations.md)を参照してください。R2の線形ファイルと、利用者が書き出す追加データファイルは別のものです。
